# Refresh the release drafts after a release

> Issue: [#43](https://github.com/chA0s-Chris/repo-baseline/issues/43)

## Rationale

`update-release-drafts.yml` runs only on pushes to `main`. A release does not push to `main`: "Release tool" and "Release profiles" create a tag and publish their own release from notes they render themselves. The drafts `tool/vNext` and `vNext` therefore keep listing the changes of the release that was just published until the next pull request is merged, as they did after tool `0.2.0` and profiles `0.7.0`.

The goal is that both drafts are current right after every release, and that the maintainer can refresh them by hand.

## Acceptance Criteria

- [ ] `update-release-drafts.yml` can be started manually and then refreshes both drafts; a manual run on a ref other than `main` changes no draft.
- [ ] After "Release tool" or "Release profiles" has published its release, both drafts are refreshed, by the release run's refresh job or by a newer refresh that replaced it while it waited.
- [ ] A refreshed draft equals what a push to `main` would render: after a stable release that is the highest version of its stream, the draft of the released stream lists no pull request that its release notes list; a pre-release or a stable release with a lower version leaves the stream's baseline unchanged.
- [ ] The refresh job runs only after the release job succeeded and never changes the published release. A failed or cancelled refresh is completed by re-running that job or by starting `update-release-drafts.yml` manually on `main`.
- [x] `AGENTS.md` (the project structure row of `update-release-drafts.yml` and "Publishing a Release") and the release paragraph of `docs/design.md` describe when the drafts are refreshed, and that a release run can end "cancelled" when a newer refresh replaced its queued one. The header and concurrency comments of `update-release-drafts.yml` and the header comments of `release-tool.yml` and `release-profiles.yml` match the new behavior. "Publishing a Release" also names a manual run of `update-release-drafts.yml` on `main` as the way to refresh the drafts or to recover from a failed refresh, and says that a run on another ref changes no draft.
- [ ] `actionlint` passes for the changed workflows in CI, and a manual run of "Release tool" and "Release profiles" on the feature branch starts and stops in `prepare` without publishing anything.

## Technical Details

**Trigger.** `update-release-drafts.yml` gets the new triggers `workflow_dispatch` and `workflow_call`, next to `push`. Both release workflows call it in a new final job that `needs: release`. A called workflow gets no more permissions than its calling job, so that job grants `contents: write` and `pull-requests: read`. No release script changes, so `tests/release/` stays unchanged. Starting the refresh with `gh workflow run` was rejected: it needs `actions: write`, and a failed refresh would not show in the release run. A called workflow runs with the caller's `workflow_dispatch` event, which release-drafter v7.11.0 already handles in the `prepare` jobs. Without `commitish`, it takes the draft's target from `github.ref`, which is `refs/heads/main`, not the release commit. Listening for `release: published` does not work: `release.sh` creates the release with `GITHUB_TOKEN`, and events created with that token start no other workflows. The refresh job is the second job of the release workflows with `contents: write`, an intended exception to the rule of plan 0030: it gets only what `update-release-drafts.yml` already had and runs only after the release job.

**Only `main`.** The update job runs only when `github.ref` is `refs/heads/main`. This guards manual dispatch on another ref; the release workflows already stop unless they run on `main`, and a called workflow sees the ref of its caller. GitHub compares strings in expressions and concurrency group names without regard to case, so a branch that differs from `main` only in case would pass the guard. Only maintainers can start the workflow, and the repository has no such branch.

**Concurrency.** The group `update-release-drafts` is shared by all triggers on `main`, so a refresh from a release and one from a merge run one after the other. Runs on other refs use their own group, whose name includes `github.ref`. GitHub assigns the workflow-level group before it evaluates the job's `if`, so a skipped run on another ref would otherwise replace a queued refresh on `main`. `cancel-in-progress` becomes `false`, so a running refresh is never cancelled. A queued refresh can still be replaced by a newer one; the release run then ends "cancelled" although everything was published. The newer run renders both drafts from the current state of `main`, so nothing needs to be re-run once it has succeeded; otherwise start `update-release-drafts.yml` manually on `main`.

**Scope of a refresh.** Every refresh updates both drafts, also after a release of only one stream; the result equals that of a push-triggered update. Pre-releases never count as the previous release (`include-pre-releases` stays false), and release-drafter compares with the highest published version of the stream, so after a pre-release the draft still lists the changes since the last stable release.

**Verification.** Release-drafter cannot run locally and no script changes, so the automated coverage is `actionlint` in CI. Before the merge, start "Release tool" and "Release profiles" by hand on the feature branch with any valid version. Each run must start, stop in `prepare` at `validate.sh` and skip the refresh job, which shows that GitHub accepts the permissions of the calling job. If GitHub allows starting `update-release-drafts.yml` on the feature branch before its manual trigger is on `main`, that run must skip its `update` job. After the merge, edit the body of one draft by hand; a manual dispatch on `main` then restores it, and its `update` job succeeds, and a manual dispatch on another branch skips the update job and changes no draft. The next release run ends with a successful refresh job, and the released stream's draft lists no pull request of its release notes, or "No changes since the last release".
